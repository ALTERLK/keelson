# 实战案例：让 Keelson 修真实项目里的真实 issue

[English](../case-study.md)

**结论先说。** 把 5 个开源项目里真实的、已被维护者修复的 issue 交给 Keelson，用项目自己的测试判分，跑了三轮：修复 3/5 → 3/5 → 4/5。这个成功数说明不了什么——样本只有 5 个，每轮每个 issue 只跑一次，同一个 issue 仅凭模型的随机性就能在两轮之间翻转。

有价值的是另一件事：**这三轮查出了 Keelson 自己的 5 个缺陷**，之前的单元测试和十几行的沙箱小题都没有暴露它们。5 个都已修复并各配了测试；另有 4 个问题没有修，原因写在[下面](#没修的问题)。其中最严重的一个是：在 Windows 上，多行 shell 命令只有第一行被执行，其余被静默丢弃——前两轮里 40 条多行命令没有一条被完整执行。

所有原始产物都在仓库里：[`bench/casestudy/`](../../bench/casestudy/) 是清单、运行器和三轮结果，15 次运行的事件流在 [`demo/traces/`](../../demo/traces/)，可以在 Web 控制台的“实战案例”页逐条回放。

## 怎么判定

用的是 SWE-bench 的协议：

1. 把项目检出到维护者修复**之前**的那个提交。
2. 只把 issue 原文交给 Keelson。它看不到随修复一起加入的测试；工作目录里也没有 `.git`，所以查不到那次修复（15 次运行里有 6 次试过 `git diff`、`git status` 或 `git log -p`，都失败了）。
3. 它停下来之后，放入维护者版本的测试文件并运行。只有**为这次修复写的测试全部通过**（fail-to-pass）、并且**原本通过的测试没有被破坏**，才算修复。

Keelson 以 `dontAsk` 模式无人值守运行：权限门本来要问人的操作一律拒绝。每个案例最多 30 步、15 分钟。模型是 `gemini-3.8-flash`，经由一个 OpenAI 兼容网关、非流式调用；机器是 Windows 11。

判分之前先验证案例本身成立（`run.py validate`，不调用模型）：在旧提交上目标测试必须失败，换上上游的修复后必须通过。5 个案例都通过了这一步；tenacity 的目标测试在旧代码上不是失败而是永不返回——那正是 bug 本身。

## 选了哪些 issue

| 项目 | issue | 问题 | 上游修复 |
|---|---|---|---|
| more-itertools | [#1308](https://github.com/more-itertools/more-itertools/issues/1308) | `bucket()` 用 `validator or default` 选校验器，一个恰好为假值的可调用对象会被悄悄换掉 | +4 −1 |
| cachetools | [#440](https://github.com/tkem/cachetools/issues/440) | `TTLCache.__setitem__` 先写入值再算过期时间；加法溢出时留下一个没有过期时间的半成品条目 | +2 −1 |
| python-dotenv | [#699](https://github.com/theskumar/python-dotenv/issues/699) | `dotenv get KEY` 对存在但为空的键返回退出码 1 | +3 −4 |
| humanize | [#205](https://github.com/python-humanize/humanize/issues/205) | `naturalsize()` 先选单位再舍入，边界下方的值显示成 `1000.0 ZB` | +6 −0 |
| tenacity | [#658](https://github.com/jd/tenacity/issues/658) | `retry_if_exception_cause_type` 遇到成环的异常链（`raise e from e`）死循环 | +7 −2 |

选取标准：纯 Python、测试离线可跑且在一分钟内、issue 有带测试的修复提交。需要如实说明的是：**这 5 个都是单文件、几行的修复，在 SWE-bench 的难度分布里属于容易的一档**，而且是我挑的，不是抽样。其中 4 个 issue 提出于 2026 年 7 月到 10 月之间。

## 结果

| | 第 1 轮 | 第 2 轮 | 第 3 轮 |
|---|---|---|---|
| 运行时 | 原样（`6e62a9e`） | 修了循环保护和空回复 | 又修了多行命令 |
| **修复的 issue** | **3 / 5** | **3 / 5** | **4 / 5** |
| 模型调用（合计） | 113 | 117 | 110 |
| 输入 Token（合计） | 140 万 | 121 万 | 152 万 |
| 撞上 30 步上限的运行 | 3 | 1 | 2 |
| 循环保护触发次数 | 6 | 1 | 0 |
| 多行 shell 命令：被完整执行 / 总数 | 0 / 30 | 0 / 10 | 3 / 6（另 3 条被明确拒绝） |
| 权限门拒绝次数 | 5 | 7 | 8 |
| 删改已有测试的运行 | 0 | 0 | 0 |

逐个 issue（✓ 修复、✗ 未修复，后面是模型调用次数）：

| issue | 第 1 轮 | 第 2 轮 | 第 3 轮 |
|---|---|---|---|
| more-itertools #1308 | ✗ 2 | ✓ 29 | ✓ 30 |
| cachetools #440 | ✓ 30 | ✗ 19 | ✓ 20 |
| python-dotenv #699 | ✓ 30 | ✓ 16 | ✓ 15 |
| humanize #205 | ✗ 30 | ✗ 30 | ✗ 30 |
| tenacity #658 | ✓ 21 | ✓ 23 | ✓ 15 |

怎么读这两张表：

- **成功数和总开销基本没变。** 3 → 3 → 4 在噪声之内；总调用数和 Token 数没有下降。我不声称这些修复“提升了成功率”。
- **变了的是具体的失败模式。** 循环保护触发从 6 次降到 0；多行命令不再被静默截断（前两轮 40 条无一完整执行，第 3 轮要么完整执行、要么明确拒绝）；第 1 轮那次“空回复就收工”没有再出现。
- **cachetools 先成功、后失败、再成功**，三轮之间与它相关的运行时逻辑并没有变坏——第 2 轮是模型自己修错了。这就是单次运行的噪声有多大。

## 查出并修掉的 5 个缺陷

每一条都按“现象 → 证据 → 原因 → 修复”来写。证据都是可回放的轨迹。

### 1. 模型返回空回复，被当成“做完了”

- **现象**：第 1 轮 more-itertools，10 秒就结束，什么都没改。
- **证据**：轨迹 `21-case-more-itertools-1308-round1`。模型列了一次文件，下一次回复既没有文字也没有工具调用（输出 0 个 token）。
- **原因**：循环的结束条件是“这次回复里没有工具调用”。空回复恰好满足它。
- **修复**：空回复（无文字、无工具调用）视为一次失败的调用，带一句提示重试，最多两次；仍然为空才结束，并发出一条警告（`agents/agent.py::_should_retry_empty_reply`，`tests/test_empty_reply.py`）。
- **验证程度**：后两轮没有再遇到空回复，所以这条修复只有单元测试，没有实际运行中的验证。

### 2. 循环保护能被模型自己重置

- **现象**：第 1 轮 cachetools，循环保护触发 4 次后，模型继续跑到了 30 步上限。
- **证据**：轨迹 `22-case-cachetools-440-round1`。模型调用了 `compact_context`，填写的理由原文是：“The previous tool calls were blocked by a loop guard, need to reset to confirm the fix.”
- **原因**：上下文折叠时会顺手清空循环保护的记录窗口，而 `compact_context` 是模型可以主动调用的工具。等于把重置按钮交给了被限制的对象。
- **修复**：折叠不再清空这个窗口。折叠改变的是模型看得到什么，不改变它刚才做了什么（`_record_fold_event`，`test_a_fold_does_not_reset_the_guard`）。

### 3. 循环保护只劝不停

- **现象**：同一次运行。保护说了 4 次“别再调工具了，给出最终答案”，模型 4 次都没听。
- **原因**：触发后只是把一句提示当作工具结果返回，没有后续动作。
- **修复**：一轮对话里触发满 3 次后，如果模型还要调工具，运行时不再执行，改为发起一次不带工具的调用让它收尾——和撞到步数上限时走的是同一条路径（`LOOP_GUARD_MAX_HITS`，`test_a_model_that_ignores_the_guard_is_stopped_by_the_runtime`）。
- **验证程度**：后两轮里单次运行最多只触发 1 次，这条路径同样只有单元测试覆盖。

### 4. 循环保护把该跑的 `pytest` 也拦了

- **现象**：还是那次运行。模型改完代码后想跑 `python -m pytest tests/test_ttl.py`，被循环保护拦下，两次。
- **原因**：保护按**工具名**计数。此前连续 6 次 `python -c` 试探让窗口里全是 `run_shell`，于是下一条 `run_shell` 不管内容是什么都被拦。但 shell 是“用来运行别的程序的工具”，按它的名字计数太粗了。
- **修复**：对 shell 命令，按“程序 + 第一个参数”计数：`python -c`、`python -m pytest`、`git diff` 各算各的（`_guard_key`）。
- **验证程度**：第 2 轮 cachetools 直接可见——保护在第 7 次相同的试探时触发，模型转去读代码、修改，随后的 `pytest` 正常执行（轨迹 `32-case-cachetools-440-round2`）。

### 5. Windows 上多行命令只执行第一行

这是第 2 轮读轨迹时才发现的，也是影响最大的一个。

- **现象**：模型写的多行复现脚本反复返回“(no output)”，于是它换着花样重试——前面几条缺陷里的“反复试探”大半源于此。
- **证据**：前两轮一共 40 条多行 shell 命令，**没有一条被完整执行**：36 条只跑了第一行，另外 4 条被循环保护拦下。例如 `python -c "` 换行再写脚本：Python 只收到一个空参数，什么也不输出。第 1 轮 python-dotenv 里模型写了四行命令（建文件、写入、读取、打印退出码），以为都跑了，其实只跑了第一行。
- **原因**：`run_shell` 把命令原样交给平台的 shell。POSIX 的 `sh -c` 会逐行执行；Windows 的 `cmd /c` 只执行第一行，其余丢弃，不报错。
- **修复**：在 Windows 上，多行命令写进一个临时批处理文件再执行，每一行都会跑，`%errorlevel%` 也按行展开。跨行的引号字符串在 cmd.exe 里无法表达，这种命令直接拒绝并说明原因，同时给出可行的写法（`agents/tools.py::_prepare_shell_command`、`_multiline_quote_problem`，`tests/test_shell_multiline.py`）。
- **验证程度**：第 3 轮 6 条多行命令：3 条被明确拒绝并说明原因，3 条完整执行。cachetools 那次，模型在被拒绝后两次调用之内就换成了提示里建议的写法，拿到了真实的报错栈，20 次调用收工、循环保护一次没触发。tenacity 那次，一条多行 `echo` 写出了 33 行的测试文件，整次运行 15 次调用，是三轮里最短的。

## 没修的问题

### 输出略有不同的空转（humanize，三轮都失败）

三轮里模型都是连续 24–26 次用 `python -c` 探测同一个浮点精度问题，一个文件都没改，直到撞上 30 步上限。循环保护一次都没触发：它判断“没有新信息”的方式是比较结果的哈希，而这些探测每次的输出都差一点。

为什么不修：要修就得把“结果相同”换成“结果相似”，或者加一个“连续多少次只读探测而没有任何修改”的预算。两者都是阈值。在同一批 5 个 issue 上调出一个刚好能拦住 humanize 的阈值，再用这 5 个 issue 证明它有效，是在测试集上调参。这一条先记下来，等有独立的样本再做。

### 权限门不是沙箱

`write_file` 新建文件在 `dontAsk` 下会被拒绝。但第 2、3 轮里模型被拒绝之后，改用 `echo … > 文件` 在 shell 里建了文件；`del` 被拒绝之后，改用 `python -c "os.remove(…)"` 删掉了文件。权限门看的是一次调用的文本，模型换一种写法就过去了。

这不是一个能靠多加几条规则堵上的洞——shell 里表达“写一个文件”的方式是无穷的。结论是：**权限门能挡住无意的危险操作，挡不住一个执意要做的模型；真正的隔离要靠操作系统层面的沙箱**（容器、受限用户）。这次实验之所以放在一次性的临时克隆里跑，也是这个原因。已记入[设计取舍](../design-tradeoffs.md)。

### 从网络安装包不需要确认

第 1 轮 python-dotenv，模型执行了 `pip install "python-dotenv[cli]"`，权限门放行了：它的危险命令清单针对的是破坏性操作（`rm`、`git push`、`kill`……），不包括联网安装。这次它装的恰好是被测项目的发行版，如果不处理，判分时测到的就是 PyPI 上已修好的代码而不是模型的改动——运行器因此在判分前会重新把环境指回工作目录。

### 修错了，而现有测试查不出来

第 2 轮 cachetools，模型把过期时间的计算放在了写入之后，半成品条目依然会留下。现有测试全过，它就认为完成了，没有再跑一遍自己写的复现脚本。运行时无从知道一个修复对不对；“修改之后必须重跑自己的复现”这类验证步骤也许能拦住这种情况，目前没有做。

### 不知道什么时候停

15 次运行里有 6 次撞上 30 步上限，其中 3 次其实早就改对了（第 1 轮的 cachetools 和 python-dotenv、第 3 轮的 more-itertools），只是一直在找新的东西验证。成功数因此没受影响，但 Token 白花了。

## 运行器自己也被纠正了三次

评测工具本身的错误和被测系统的错误一样需要说明：

- **把 `.git` 藏起来。** 克隆里包含修复提交。最初的版本没有处理这一点；在跑任何模型之前改成了运行期间把 `.git` 移出工作目录。
- **判分前重新安装工作目录。** 见上面“从网络安装包”一节。
- **轨迹脱敏漏了三种写法。** `pytest-of-<用户名>` 这样的目录名、被 pytest 缩写过的路径（`C:\\Users\\3...9\\repo`）、以及把 Python 源码里的 `as e:` 加换行误判成盘符 `e:`。每次都是泄露检查先拦下来、拒绝保存，然后才补的规则（`agents/web/scrub.py`，`tests/test_scrub.py`）。

## 这个实验不能说明什么

- **成功率。** 5 个 issue、每轮一次运行、一个模型、一台 Windows 机器。
- **修复带来了多少提升。** 第 2、3 轮是在同一批 issue 上重跑的，而修复正是由这批 issue 暴露的问题引出的，不是独立的测量。能说的只是：对应的失败模式在后面的轮次里消失了，并且每条修复都有一个不依赖模型的单元测试。
- **在更难的问题上的表现。** 这 5 个都是几行的单文件修复。

## 复现

```bash
python bench/casestudy/run.py validate            # 不调用模型：确认 5 个案例本身成立
python bench/casestudy/run.py run                 # 让 Keelson 跑全部案例并判分
python bench/casestudy/run.py run tenacity-658    # 或者只跑一个
python bench/casestudy/run.py grade               # 不调用模型，对已保存的改动重新判分
```

克隆和虚拟环境放在系统临时目录下（`--work` 可改）。结果写入 `bench/casestudy/results.json`，脱敏后的轨迹写入 `demo/traces/`。一轮大约 10 分钟、120–150 万输入 Token。
